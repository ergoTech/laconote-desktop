# Product Requirements Document: Аналіз проблем з дозволами на аудіо

## 1. Вступ
Цей документ фіксує результати глибинного аналізу проблем із дозволами на системне аудіо в macOS-додатку Laconote (Tauri + React + Rust) та уточнює, чому додаток може не реагувати на вже наданий дозвіл у `System Settings -> Privacy & Security -> Screen & System Audio Recording`.

## 2. Контекст і симптоми
**Симптоми:**
1. Користувач вмикає дозвіл для Laconote у `Screen & System Audio Recording`.
2. У системних налаштуваннях тумблер виглядає увімкненим.
3. У самому додатку статус системного аудіо лишається `Не налаштовано` або `Потрібна перевірка`.
4. Після натискання `Open Settings` і повернення в додаток іноді немає жодної видимої зміни, ніби дозвіл не був наданий.

## 3. Висновок аналізу
Проблема складається **з двох окремих шарів**, які зараз накладаються один на одного:

### 3.1. Проблема рівня macOS / TCC / code signing
macOS TCC перевіряє не лише `Bundle ID`, а й **стабільність code signature** застосунку.

- У проєкті використовується `identifier = "com.laconote.desktop"` у `src-tauri/tauri.conf.json`.
- Під час локальної розробки без Developer ID застосунок збирається з ad-hoc підписом.
- Після нового білду Rust/macOS-бінарник змінюється, і macOS може трактувати його як інший екземпляр застосунку.
- Через це раніше наданий дозвіл у TCC стає непридатним для нової збірки, навіть якщо в UI System Settings здається, що Laconote вже дозволений.

**Наслідок:** без стабільного підпису дозволи можуть “зникати” між білдами або поводитися нестабільно.

### 3.2. Проблема рівня застосунку / логіки перевірки readiness
Навіть коли дозвіл у TCC вже фактично виданий, поточна логіка застосунку може **не показати цього в UI**.

#### Факт 1: `check_permissions()` ніколи сам по собі не повертає `system_audio = granted`
У `src-tauri/src/permissions.rs`:
- `CGPreflightScreenCaptureAccess()` визначає лише `screen_capture_access`.
- `system_audio_capture_ready` примусово встановлюється в `Unknown`.
- `derive_system_audio_status()` при `Unknown` теж повертає `Unknown`.

Тобто звичайний `check_permissions()` **не здатний підтвердити granted-стан для системного аудіо**, навіть якщо системний дозвіл уже є.

#### Факт 2: UI вважає системне аудіо “granted” лише після успішного `probe_system_audio_capture`
У `src/components/PermissionOnboarding.tsx`:
- після відкриття системних налаштувань фронтенд запускає `probe_system_audio_capture`;
- лише якщо probe повертає `ready`, UI вручну мержить статус у `granted`.

#### Факт 3: probe має надто жорстке визначення успіху
У `src-tauri/src/audio/cat_tap.rs` probe вважається успішним лише якщо:
1. `catap_start()` стартує без помилки;
2. протягом `1200ms` приходять **непорожні audio frames**.

Якщо:
- у системі в цей момент немає звуку;
- callback не встиг отримати буфер за 1.2 секунди;
- CATap стартував, але повернув порожній фрейм;

тоді результат буде `Unknown`, а фронтенд **не покаже жодної позитивної зміни**, хоча дозвіл може бути вже наданий.

#### Факт 4: recording-flow трактує `Unknown` м’якше, ніж onboarding/UI
У `src-tauri/src/recording.rs`:
- `CaptureReadiness::Ready` — ок;
- `CaptureReadiness::Unknown` — логічно вважається inconclusive, і код **продовжує запуск live capture**;
- `CaptureReadiness::NotReady` — лише тоді зупиняється з помилкою.

Це означає, що **onboarding/UI зараз суворіший і менш інформативний, ніж реальний recording-path**. Саме тому користувач має відчуття, що “нічого не змінилося”, хоча бекенд у деяких випадках уже вважає стан достатнім для спроби запису.

## 4. Відповіді на ключові питання

### 4.1. Чи обов’язково потрібен офіційний Apple Developer Certificate?
**Для продакшену — так, обов’язково.**

**Для локальної перевірки однієї конкретної збірки — ні, не обов’язково.**
Але без стабільного сертифіката буде нестабільна поведінка TCC між різними білдами.

Отже:
- **щоб просто разово протестувати один зібраний `.app`** — можна і без платного сертифіката;
- **щоб macOS стабільно пам’ятала дозвіл між релізами/білдами** — потрібен стабільний Developer ID підпис;
- **щоб дистриб’ютити застосунок користувачам** — Developer Program практично обов’язковий.

### 4.2. Чи вирішить проблему переписування на нативний Swift/AppKit?
**Ні.**
Нативний додаток теж працює через той самий TCC. Без стабільного підпису проблема збереження дозволів між білдами не зникне.

### 4.3. Де це налаштовується?
У поточному проєкті вже є базові точки конфігурації macOS-збірки:
- `src-tauri/tauri.conf.json` — `identifier`, bundle-конфіг, `Info.plist`, `entitlements.plist`;
- `src-tauri/entitlements.plist` — entitlement-и для macOS;
- реальний signing certificate налаштовується **не у React-коді**, а на рівні macOS/Xcode/Keychain/Tauri build environment.

Тобто проблема не в тому, що “немає місця в коді для дозволу”, а в тому, що:
1. macOS permission model залежить від підпису;
2. поточний код застосунку не відображає granted-стан достатньо надійно.

## 5. Вимоги до наступного етапу
На наступному етапі потрібно не переписувати застосунок на нативку, а уточнити та покращити permission-flow.

### Функціональні вимоги
1. Застосунок має **чітко відділити**:
   - `OS permission granted by TCC`;
   - `audio tap readiness verified by live probe`.
2. UI має показувати, коли дозвіл **вже наданий**, навіть якщо readiness probe не зміг підтвердити активний аудіопотік.
3. UI має пояснювати різницю між станами:
   - дозвіл не надано;
   - дозвіл надано, але немає підтвердженого аудіосигналу;
   - аудіозахоплення повністю готове.
4. Для локальної dev-збірки UI має явно попереджати, що після нового білду TCC може потребувати повторного підтвердження.

### Нефункціональні вимоги
1. Діагностика має бути придатною для дебагу: треба зберігати/показувати причину `probe.detail` і OSStatus-помилки.
2. Перевірка не повинна залежати лише від факту, що в системі зараз грає звук протягом дуже короткого таймауту.
3. Поведінка onboarding та recording-flow має бути узгодженою.

## 6. Рекомендації
1. **Не переписувати на нативку** — це не вирішить кореневу проблему.
2. **Не робити висновок, що причина лише в сертифікаті** — у поточній реалізації є ще й логічна проблема з детекцією `granted`.
3. Для продакшену закласти **Apple Developer Program / Developer ID signing**.
4. Для dev-режиму передбачити окремий UX/діагностику, який пояснює нестабільність TCC після rebuild.
5. У наступній технічній специфікації сфокусуватись на переробці permission state model, а не на зміні стеку застосунку.
